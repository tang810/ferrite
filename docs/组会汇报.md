# 组会汇报：薄铁氧体屏蔽仿真流水线搭建与验证

2026-05-27

## 一、起点：B0_reference_x 重建

项目需要一组可信的 x 向无屏蔽参考基准。盘了现有数据后发现 `analysis_ready/manufacturable_thin_center_fields_exported.csv` 里 C1_N1_t008 行有一组 B0 导出，但数据方向不对——B0_Bx_T = -1.65e-08, B0_Bz_T = 3.33e-08，z 分量居然比 x 分量大一倍。对 x 向外场来说这是错的，说明这组 B0 不可用。

于是从 C1_N1_t008_shield.aedt 复制了模板，删掉 torus/current 外场，把 Cylinder2 改成 vacuum，在 Box1 的 y/z 面加 x 向切向 H 场（H0=1 A/m），x 端面加零切向 H 场作开放磁通边界。求解导出后验证：B0_Bx_T = 1.2566e-06 T，方向比 6.47e+06（x 分量比最大横向分量大 6 个数量级），确认为纯 x 向外场。这个 B0_reference_x 存为 `aedt/reference/B0_reference_x.aedt`，导出放到 `data/raw/B0_reference_x.csv`，验证通过。

## 二、问题诊断：shield 工程外场方式不一致

有了可信的 B0 之后，需要确认 7 个 shield 工程（4 个单层 + 3 个多层）的外部场设置是否跟 B0_reference_x 一致。读了 `round2_working/run_manufacturable_thin_continuous.log` 的日志，发现所有 shield 工程用的是 torus/current 方式——在铁氧体壳外画铜环 (Torus2/Torus3)，通 1A 电流产生外场，还加了 Iext_plus/minus 电流片。

问题在于：torus/current 和 tangential-H 是两种不同的物理边界条件，前者用电流源激励，后者直接在边界上约束切向 H 场。两个不同边界条件下算出的 Bcenter 不能直接跟 B0_reference_x（切向 H）比。这就是之前数据里算出来 SF=0.6265（居然小于 1，物理上不可能）的原因。

结论：所有 7 个 shield 工程必须重建为 x 向切向 H 外场，才能跟 B0_reference_x 对齐。

## 三、核心脚本：rebuild_shields_tangentialH.py

写了一个完整的 AEDT ScriptEnv 脚本（IronPython 2.7），放在 `scripts/aedt_export/rebuild_shields_tangentialH.py`，全长约 440 行。在 AEDT 菜单栏 Tools → Run Script 加载运行。

每个 shield 工程的处理流程分 9 步：

1. 删 .aedt.lock — 前一次 AEDT 崩溃或非正常退出残留的锁文件会阻止 OpenProject
2. OpenProject — 打开 `round2_working/manufacturable_thin/` 下的 .aedt 工程
3. delete_old_boundaries — 调 GetExcitations/GetBoundaries 拿现有激励和边界列表，逐个 DeleteBoundaries。同时硬编码补删 Iext_plus/minus、Current1/2（历史命名的残余）
4. cleanup_geometry — 删 Torus2、Torus3、Iext_plus/minus_sheet 等旧外场几何体（共 11 种可能的名字）
5. ensure_ferrite_material — 遍历 Cylinder2/4/6/8，确认材料是 ferrite 且 Solve Inside = True（之前有些工程在重建过程中被误改成了 vacuum）
6. assign_x_tangential_h — 读 Box1 的所有面 ID 和中心坐标，按法向分成 x/y/z 三组。y/z 面（法向非 x）逐一调 AssignTangentialHField(ComponentXReal=1, ComponentYReal=0)，配套 CoordSysVector 指定原点和方向。x 端面统一调 AssignZeroTangentialHField 作开放磁通边界
7. ValidateDesign + Analyze Setup1 — 验证设计无几何冲突后求解
8. export_center_field — 调 FieldsReporter 计算器，走 CalcStack("clear") → EnterQty("B") → CalcOp("ScalarX/Y/Z") → EnterPoint("BcenterPoint_0_0_0") → CalcOp("Value") → GetTopEntryValue 路径，依次取 Bx/By/Bz/Mag，追加到 `data/raw/center_field_raw.csv`
9. export_intH2 — 调 CopyNamedExprToStack 取命名表达式 IntH2_total 和各层 IntH2_Li，追加到 `data/raw/intH2_layerwise_raw.csv`

分两批运行：第一批 4 个单层 case（C1_N1_t008_x 到 t060_x），全部通过后用户确认继续，再跑第二批 3 个多层 case（C2_N2_t020_g010_x, C2_N3_t020_g010_x, C2_N4_t015_g008_x）。

此外，`scripts/aedt_export/` 下还有两个 pyAEDT 版导出脚本（export_center_field.py、export_intH2_layerwise.py），之前只有 RuntimeError 占位，也一并实现了。用 ofields.evaluate_at_point() 和 ofields.evaluate_expression() 分别取中心场和命名表达式。这两个脚本用在不需要重建工程、只需重新导出的场景。

## 四、后处理流水线

导出 7 个 case 的原始数据后，依次跑三个后处理脚本：

4.1 build_dataset.py

输入 B0_reference_x.csv + center_field_raw.csv + intH2_layerwise_raw.csv + 实验矩阵定义，合并成 manufacturable_thin_dataset.csv 和 metrics_table.csv。核心计算：SFx = |B0_Bx_T| / |Bcenter_Bx_T|，LeakageRatiox = 1/SFx。Mag_B 只做辅助检查，正式 SF 用方向分量算。

4.2 compute_metrics.py

读取 metrics_table.csv，补充衍生指标：Vf（铁氧体体积，通过几何参数计算），etaS = ln(SFx)/Vf（单位体积屏蔽效率），etaS_star = etaS/mu_r（材料归一化效率），rhoH = IntH2_total/Vf（铁氧体内部平均 |H|²），chiH = rhoH/mu_r。写完回 metrics_table.csv。

4.3 validate_layerwise_intH2.py

校验每层 IntH2_Li 之和是否等于 IntH2_total。判据：|total - sum(Li)| / |total| < 1e-3。不通过的不能标 used_in_paper。所有 7 个 case 的 relative_error 都在 1e-12 量级或精确为 0，全部 passed。

## 五、踩过的坑（4 个关键 bug）

坑 1：所有 OpenProject 调用失败。错误信息 "Project is already open or locked by another process"。原因排查：每次 AEDT 非正常退出后 .aedt.lock 文件残留，AEDT 认为工程还被占用。修复：在 process_case() 开头用 os.path.exists + os.remove 清理 lock。

坑 2：IronPython CSV 写文件报 TypeError: open() takes at most 3 arguments (4 given)。原因：我起初按 CPython 习惯写了 open(path, "w", newline="", encoding="utf-8")，但 IronPython 2.7 的 open() 只接受 (path, mode, buffering) 三个参数。修复：改用 binary mode "wb"（新文件）和 "ab"（追加），IronPython 2.7 的 csv.DictWriter 在 binary mode 下正常工作。

坑 3：多层 case 的 IntH2_L1 数值等于 IntH2_total。原因排查：我在 IntH2 导出函数里给每层做了 legacy 命名候选列表。单层时 L1 的唯一来源就是总量，所以 L1 候选里放了 IntH2_total 作 fallback。但多层时这个 fallback 也被继承了——L1 先试 IntH2_L1，没找到就试 IntH2_total，而 IntH2_total 总是存在的，多层 L1 就会错误地取到总量值。修复：按 layers == 1 vs layers > 1 分支。单层保持 L1 候选包含 IntH2_total（因为单层确实 L1=total），多层 L1 候选移除 IntH2_total。重跑后多层数据修正。

坑 4：命名表达式找不到。单层 case 按 IntH2_L1 找，AEDT 返回空。原因：模板工程里 IntH2 用的是历史名字。N=1 的工程用了 IntH2_s1 和 IntH2_cyl2；多层工程更乱，N=2 有 IntH2_cyl2/cyl4，N=3 有 IntH2_s1/s2/s3，N=4 有 IntH2_s1/s2/s3 和 InH2_s4（注意第 4 层拼成了 In 不是 Int，是之前手动操作时的笔误）。修复：给每层做了一个 legacy 候选列表，按层号映射（L1 试 IntH2_L1 → IntH2_s1 → IntH2_cyl2 → InH2_s1，L2 试 IntH2_L2 → IntH2_s2 → IntH2_cyl4 → InH2_s2，L3/4 类推），逐个 TryGetEntryValue 直到找到。

## 九、技术积累

IronPython 2.7 限制：
- open() 只接受 3 个参数，Python 3 的 newline/encoding 都不支持
- csv.DictWriter 要用 binary mode
- ScriptEnv 入口固定写法 `import ScriptEnv; ScriptEnv.Initialize("Ansoft.ElectronicsDesktop")`
- 跑之前检查 .aedt.lock 必须清掉

AEDT FieldsReporter 用法：
- 场量：CalcStack → EnterQty → CalcOp(ScalarX/Y/Z/Mag) → EnterPoint → CalcOp(Value) → GetTopEntryValue
- 命名表达式：CopyNamedExprToStack → ClcEval → GetTopEntryValue
- CalcStack("clear") 每次开头清栈，不然残留栈会影响下一次计算

命名表达式规范：
- 新建工程：IntH2_total = sum(IntH2_Li)，每层 IntH2_L1, IntH2_L2, ...
- 旧工程可能有 IntH2_cyl2/cyl4, IntH2_s1/s2/s3/s4, InH2_s4（拼写错误）
- 导出脚本要做 multi-candidate fallback，按层映射到规范名
